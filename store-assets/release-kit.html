Data safety

App content → Data safety

The section reviewers scrutinise hardest for a screen-capture app. Below is what the code actually does, so you can answer accurately — you're the one signing this declaration, so read it against the wording your console shows rather than pasting blind.

The screen video itself

Captured via MediaProjection, encrypted by WebRTC (DTLS-SRTP) and sent to the one viewer who opened the user's link. It is never written to a Layerbit server and never stored anywhere by the app. Play does not treat a transfer made on a specific user-initiated action, to a recipient the user chose, as "sharing" — which is exactly what a broadcast is here.

Connection metadata → Firebase Realtime Database

A random 6-character session ID plus the WebRTC handshake (SDP offer/answer and ICE candidates, which include the device's network addresses). Used only to introduce the two ends to each other, tied to no account or identity, and deleted the moment the session stops.

The TURN relay — worth knowing before you answer

When a direct peer-to-peer path can't be established, the encrypted media falls back to relaying through openrelay.metered.ca, a free third-party TURN server. It forwards encrypted packets and cannot decrypt or store them, but it is a third party in the path — so don't describe the app as strictly device-to-device in a way that contradicts this.

Is all collected data encrypted in transit?

Yes. HTTPS to Firebase for signalling; DTLS-SRTP for the media stream.

Can users request data deletion?

There's no account to delete. Session data is anonymous and removed automatically when the broadcast ends — state exactly that if the form gives you a free-text box.

Everything else

Not collected: name, email, address, phone, financial info, health, messages, photos stored on the device, contacts, calendar, files, audio, browsing history, installed apps, location.

Sensitive permissions

App content → Sensitive app permissions (appears if the console asks for a declaration)

The manifest declares SYSTEM_ALERT_WINDOW and FOREGROUND_SERVICE_MEDIA_PROJECTION. If your console asks for a justification, these are accurate:

Display over other apps

LayerLink shows a small floating Stop control while a screen broadcast is active, so the user can end the session from any app without switching back to LayerLink. It appears only during an active broadcast, is draggable anywhere on screen, and asks for confirmation before stopping so an accidental tap cannot cut a session off.

Media projection foreground service

The foreground service captures and transmits the user's screen in real time — this is the app's core, user-initiated feature, not background work. Android requires screen capture to run in a foreground service of type mediaProjection with an ongoing notification, so the capture is not terminated while the user moves between other apps during a broadcast.

After you hit Send for review

A first app from a brand-new developer account gets a fuller review than later updates — commonly a few days, sometimes up to a couple of weeks. Screen-capture apps sit in a closely-reviewed category, so the two things most likely to come back at you are a privacy policy that doesn't match the Data safety answers, and the permissions justifications. Both are handled above.

You'll get the decision by email on the account. If it's rejected, the notice names the specific policy — send it to me and we'll work the fix.
